## Premise (P0) — Confirmed on base `ff99142f`

Claimed symptom (quoted from the PR body): "The Curvine sample does not work
when followed as written" — `${CURVINE_HOME}/conf` "ends up as `/conf`", and
`curvine/curvine:0.3.6-alpha` "does not exist on Docker Hub".

Reproduced by executing the doc's own heredocs at the base ref exactly as a
user's shell would (`results/premise-base.out`):

- `CURVINE_CONF_DIR="${CURVINE_HOME}/conf"` → written to the file as `CURVINE_CONF_DIR="/conf"`
- `set -ex; test -n "$(cat /data/minio/bar)"` → written as `set -ex; test -n ""`
  (local `cat: /data/minio/bar: No such file or directory`) — the job would fail
  in-cluster for the wrong reason before ever touching the cache
- `curvine/curvine:0.3.6-alpha` → HTTP 404 at registry-1.docker.io; the tag list
  for `curvine/curvine` contains only `v`-prefixed tags
- Component match: yes — the PR touches exactly the two files that carry the bug.

**Verdict: Confirmed.** The problem is real, and the fix targets it.

## F2 — remaining (pre-existing) defect, non-blocking

Step 6 of the sample (both languages):

```shell
$ kubectl get pod -l cacheruntime.fluid.io/runtime-name=curvine-demo
```

No component pod carries that label. `pkg/common/label.go` defines
`cacheruntime.fluid.io/name` and `cacheruntime.fluid.io/component-name`
(set by `GetComponentMatchLabels`); `test/gha-e2e/curvine/test.sh` selects pods
with exactly those keys. The command prints `No resources found in default
namespace`, confusing readers at the "check the cluster" step. This exists on
the base branch, is outside this PR's declared scope (heredocs + image tag),
and was already recorded by the PR #6253 review round — recommend a one-line
follow-up PR (`-l cacheruntime.fluid.io/name=curvine-demo`), not blocking #6252.
